# 常量统一管理实现报告

## 概述

成功完成项目中分散常量的统一管理，将原本分布在各个模块文件中的常量定义集中到 `internal/consts/` 目录下，实现了常量的统一维护和管理。

## 实施背景

### 重构前问题
- ❌ **常量分散**: Task、Device、Queue模块中各自定义相同或相关常量
- ❌ **重复定义**: 多个文件中存在相同的状态、类型常量定义
- ❌ **维护困难**: 修改常量需要在多个文件中同步更新
- ❌ **不一致风险**: 不同模块间常量值可能存在差异

### 重构目标
- ✅ **集中管理**: 将所有常量统一管理在consts包中
- ✅ **消除重复**: 避免常量定义的重复和冲突
- ✅ **便于维护**: 修改常量只需在一个地方进行
- ✅ **确保一致**: 所有模块使用相同的常量定义

## 实施方案

### 1. 常量分类整理

按照模块功能将常量分为4个文件：

#### `internal/consts/common.go` - 通用常量 (122行)
- **系统常量**: 系统名称、版本、API版本
- **HTTP状态**: 成功、错误、待处理状态
- **分页常量**: 默认页面大小、最大页面大小  
- **时间格式**: RFC3339、日期、时间、完整格式
- **文件大小**: KB、MB、GB、TB单位
- **数据库常量**: 超时、连接数、生命周期
- **缓存常量**: TTL时间、重试次数、重试间隔
- **网络常量**: 超时时间、重试参数
- **验证常量**: 字符串长度、密码长度限制
- **错误码常量**: HTTP错误码定义
- **ID生成常量**: 前缀、长度定义
- **正则表达式**: 邮箱、手机、IP、设备ID格式
- **环境常量**: 开发、测试、预发、生产环境

#### `internal/consts/task.go` - 任务模块常量 (77行)  
- **任务状态**: 9种状态（pending→queued→assigning→assigned→dispatching→running→completed/failed/canceled）
- **任务类型**: backup、sync、monitor、custom
- **执行器类型**: local、remote、container、lambda
- **执行状态**: 5种执行状态
- **队列状态**: 队列中的任务状态
- **分配动作**: 6种分配历史动作
- **依赖类型**: before、after、parallel依赖
- **优先级**: 1-10优先级等级定义
- **重试常量**: 默认重试次数、最大重试、默认超时
- **调度常量**: 调度间隔、最大并发、批处理大小

#### `internal/consts/device.go` - 设备模块常量 (95行)
- **设备状态**: online、offline、maintenance、error
- **设备类型**: sensor、camera、actuator、gateway
- **认证类型**: 7种认证方式（none、basic、token、bearer、oauth2、apikey、certificate）
- **通信协议**: 8种协议（http、https、tcp、udp、mqtt、coap、modbus、bacnet）
- **日志级别**: debug、info、warn、error、fatal
- **命令状态**: 6种命令状态
- **命令类型**: 8种命令类型
- **健康度常量**: 0-100范围、默认值、阈值
- **心跳常量**: 不同设备类型的心跳间隔
- **连接常量**: 超时时间、重试次数、重试间隔
- **负载常量**: 正常、警告、严重负载阈值
- **端口范围**: 1-65535
- **配置常量**: 默认队列大小、并发数、超时时间

#### `internal/consts/queue.go` - 队列模块常量 (72行)
- **队列状态**: 6种队列任务状态
- **操作类型**: 8种队列操作
- **调度策略**: 4种调度策略
- **操作来源**: 4种操作来源
- **优先级**: 1-10优先级等级
- **配置常量**: 队列大小、并发限制、批处理限制
- **超时常量**: 默认、最小、最大超时时间
- **重试常量**: 重试次数范围
- **监控常量**: 监控间隔、健康检查间隔、指标收集间隔

### 技术收益

#### 1. 可维护性提升
```go
// 重构前：需要在多个文件中修改
// internal/biz/task/models.go
const TaskStatusPending = "pending"

// internal/biz/device/models.go  
const DeviceStatusOnline = "online"

// internal/biz/queue/models.go
const QueueStatusQueued = "queued"

// 重构后：只需在一个地方修改
// internal/consts/task.go
const TaskStatusPending = "pending"

// 其他文件引用
const TaskStatusPending = consts.TaskStatusPending
```

#### 2. 一致性保证
```go
// 重构前：可能存在不一致
// 文件A: TaskStatusCompleted = "completed"
// 文件B: TaskStatusCompleted = "finish"  // 不一致！

// 重构后：确保一致性
const TaskStatusCompleted = consts.TaskStatusCompleted // 统一来源
```

#### 3. 智能提示改善
```go
// IDE可以提供完整的常量列表
consts.TaskStatus... // 自动补全所有任务状态
consts.DeviceType... // 自动补全所有设备类型
consts.Protocol...   // 自动补全所有协议类型
```

### 向后兼容性

为确保平滑迁移，采用了渐进式重构策略：

```go
// 保持本地常量定义，但指向统一常量
const (
    TaskStatusPending = consts.TaskStatusPending  // 向后兼容
    TaskStatusQueued  = consts.TaskStatusQueued   // 向后兼容
    // ...
)
```

这样做的好处：
- ✅ **零破坏性**: 现有代码无需修改，继续正常工作
- ✅ **渐进迁移**: 可以逐步将代码迁移到直接使用consts包
- ✅ **风险可控**: 降低大规模重构的风险

## 最佳实践

### 1. 常量命名规范
```go
// 模块前缀 + 功能 + 具体值
const TaskStatusPending = "pending"
const DeviceTypeSensor = "sensor"
const CommandTypeStart = "start"
```

### 2. 分组组织
```go
// 按功能分组，添加注释说明
// 任务状态常量
const (
    TaskStatusPending     = "pending"
    TaskStatusQueued      = "queued"      // 已入队待分配
    TaskStatusAssigning   = "assigning"   // 分配中
    // ...
)
```

### 3. 使用方式
```go
// 推荐：直接使用consts包（新代码）
import "github.com/YoungBoyGod/OneGoServer/internal/consts"
if task.Status == consts.TaskStatusCompleted {
    // ...
}

// 兼容：通过本地常量（现有代码）
if task.Status == TaskStatusCompleted {
    // ...
}
```
