下面按照 “GoFrame + 分层服务” 风格，对 User、Device、Task 三大模块下各接口的调用流程做最细化的拆解，明确涉及的组件（配置、数据库、缓存、消息队列、日志、指标等）以及每一步的职责。

---

## 一、公共依赖组件说明

* **配置管理（configs/\*.toml + Viper）**
  一切业务参数（例如分页默认 `pageSize`、缓存 TTL、Kafka topic 名称）都从 Viper 加载，按 `config.development.toml` / `config.production.toml` 覆盖。

* **日志（pkg/logger/zap.go）**
  每个 Handler 和 Service 都注入全局 Logger，记录 `RequestID`、用户标识、接口名、入参、出参、耗时。

* **缓存（pkg/cache/redis.go）**
  用户列表、设备详情、任务状态等热点数据优先读 Redis。缓存 key 前缀在配置中统一定义，比如 `user:detail:{id}`。

* **数据库（internal/model/* + GoFrame gdb）*\*
  真正的 CRUD 操作都在 `internal/service/*.go` 里调用 `g.DB().Model(&Model{})...` 完成，所有 SQL 都由 Migration 管理。

* **消息队列（pkg/kafka/producer.go）**
  在任务创建/取消、设备上下线等需要异步通知的场景，将事件序列化后推送到 Kafka，供其他微服务或审计系统消费。

* **指标（Prometheus + internal/handler/metrics.go）**
  关键接口都会在业务逻辑入口和出口处打点，统计 QPS、响应时长（Histogram）、错误率（Counter）。

## 二、用户管理模块 `/api/v1/user`

### 1. 用户列表 `/user/list`

**功能**：分页、筛选后返回用户基本信息列表

**流程**

1. **接收请求**

   * 路由：`GET /api/v1/user/list?page=&size=&name=`
   * Gin 自动绑定 `page`/`size`/`name`，并做非空、范围校验（validator）。

2. **鉴权 & 权限校验**

   * 中间件读取 JWT，解析用户角色，确认是否有 `user:list` 权限。

3. **缓存检查**

   * 构造 Redis key：`user:list:{page}:{size}:{name}`
   * 如果命中，反序列化 JSON，直接返回（日志打 `cache_hit=true`）。

4. **DB 查询**

   * `g.DB().Model(&User{}).Where("name LIKE ?", "%name%").Page(page, size).Scan(&[]User{})`

5. **缓存写入**

   * 将结果序列化写入 Redis，TTL=配置值（如 60s）。

6. **返回结果**

   * 按约定的分页 DTO 返回，写入 Prometheus Histogram 和 Counter。

---

### 2. 用户详情 `/user/detail/:id`

**功能**：返回单个用户完整信息

**流程**

1. **接收请求**

   * 路由：`GET /api/v1/user/detail/:id`，`id` 通过 `ShouldBindUri` 校验 UUID 格式。

2. **鉴权**

   * JWT 校验，确保有 `user:detail` 权限。

3. **缓存检查**

   * Key：`user:detail:{id}`，存在则直接返回。

4. **DB 查询**

   * `g.DB().Model(&User{}).Where("id=?", id).Scan(&user)`
   * 如果未查到，返回统一错误码 `USER_NOT_FOUND`。

5. **缓存写入**

   * 序列化 `user` 到 Redis，TTL=配置值。

6. **返回结果**

   * 返回用户详情 DTO，包括 `id, name, email, roles, created_at`。

---

### 3. 用户创建 `/user/create`

**功能**：新增一条用户记录

**流程**

1. **接收请求**

   * 路由：`POST /api/v1/user/create`，Body 绑定 `UserCreateReq`（包含 `name, email, password`），并校验字段格式。

2. **鉴权**

   * 确认用户具有 `user:create` 权限。

3. **密码加密**

   * 调用 `pkg/crypto.HashPassword(req.Password)`。

4. **DB 插入**

   * `g.DB().Model(&User{}).Data(req).Insert()`
   * 插入失败（如 `email` 唯一约束）捕获并转换为业务错误。

5. **缓存清理**

   * 删除 `user:list:*` 全表相关缓存。

6. **返回结果**

   * 返回新用户 `id`，写日志、指标。

---

### 4. 用户编辑 `/user/edit/:id`

**功能**：修改指定用户信息

**流程**

1. **接收请求**

   * 路由：`PUT /api/v1/user/edit/:id`，URI 绑定 `id`，Body 绑定 `UserEditReq`。

2. **鉴权**

   * `user:edit` 权限校验。

3. **DB 预查询**

   * `g.DB().Model(&User{}).Where("id=?", id).Scan(&user)`
   * 若不存在，返回 `USER_NOT_FOUND`。

4. **DB 更新**

   * `g.DB().Model(&User{}).Where("id=?", id).Data(req).Update()`。

5. **缓存清理**

   * 删除 `user:detail:{id}`，`user:list:*`。

6. **返回结果**

   * 返回更新后的 DTO。

---

### 5. 用户删除 `/user/delete/:id`

**功能**：移除指定用户

**流程**

1. 接收 + 鉴权 同编辑
2. DB 预查询，若不存在报错
3. DB 删除或软删除（`deleted_at` 置非空）
4. 缓存清理：`user:detail:{id}`, `user:list:*`
5. 写 Kafka 事件：`topic="user.events"`, payload `{ event:"deleted", id }`
6. 返回状态

---

### 6. 用户查询 `/user/query`

**功能**：根据任意字段（如 email）查询单个用户

**流程**

1. 接收 `GET /api/v1/user/query?email=`
2. 鉴权 `user:detail`
3. 缓存检查 Key=`user:query:email:{email}`
4. DB 查询 `Where("email=?", email)`
5. 缓存写入、返回或报错

---

### 7. 用户任务查询 `/user/task/list`

**功能**：获取某用户名下所有任务

**流程**

1. 接收 `GET /api/v1/user/task/list?user_id=&page=&size=`
2. 鉴权 `task:list`
3. **DB 联表查询**

   ```sql
   SELECT t.* 
   FROM tasks t 
   JOIN users u ON t.user_id = u.id 
   WHERE u.id = ? 
   ORDER BY t.created_at DESC 
   OFFSET ? LIMIT ?
   ```
4. 可选：将结果缓存至 Redis，Key=`user:task:list:{user_id}:{page}:{size}`
5. 返回分页结果

## 三、设备管理模块 `/api/v1/device`

下面将共用的“预查询→变更→缓存清理→消息通知”模式简化描述，重点各接口差异。

| 接口                          | 描述                  | 关键流程                                                                                         |
| --------------------------- | ------------------- | -------------------------------------------------------------------------------------------- |
| **注册** `/device/register`   | 设备初次注册              | 1.校验硬件指纹 → 2.DB 插入/更新设备记录 → 3.写缓存(`device:detail:{id}`) → 4.发送 Kafka 事件(`device.registered`) |
| **上线** `/device/online`     | 设备主动上线（心跳首次到达）      | 1.接收 `device_id` → 2.更新 `status=online,last_seen` → 3.缓存更新 → 4.指标 `device_online_total++`    |
| **下线** `/device/offline`    | 管理端强制下线             | 1.校验权限 → 2.更新 `status=offline` → 同上缓存+事件(`device.offlined`)                                  |
| **心跳** `/device/heartbeat`  | 定时心跳（客户端定期上报）       | 1.接收心跳 → 2.预查询设备是否存在 → 3.更新 `last_seen` → 4.缓存更新 → 5.返回 `OK`                                 |
| **状态** `/device/status`     | 获取多设备在线/离线统计        | 1.从 Redis 统计 `device:status:counts` → 若缓存过期则 DB count 聚合 → 2.返回统计结果                          |
| **日志** `/device/log`        | 采集或查询设备日志           | - **采集**：Bulk POST，写入 ELK（Filebeat→Logstash→Elasticsearch）<br>- **查询**：ES DSL 查询+分页          |
| **统计** `/device/stats`      | 设备各类指标（CPU/MEM/任务数） | 1.从 Prometheus 查询多维度指标 → 聚合后返回                                                               |
| **查询** `/device/query`      | 任意字段查询单台设备          | 类似 `/user/query`                                                                             |
| **列表** `/device/list`       | 分页设备列表              | 类似 `/user/list`，默认按 `last_seen` 降序                                                           |
| **详情** `/device/detail/:id` | 单台设备详情              | 类似 `/user/detail/:id`                                                                        |
| **创建** `/device/create`     | 后端管理手动创建设备（非注册）     | 类似 `/user/create`                                                                            |
| **编辑** `/device/edit/:id`   | 更新设备基本属性            | 同 `/user/edit/:id`                                                                           |
| **删除** `/device/delete/:id` | 移除设备（软删除）           | 同 `/user/delete/:id` but topic=`device.deleted`                                              |

## 四、任务管理模块 `/api/v1/task`

所有 Task API 均走同样的 “预校验→DB 操作→事件推送→缓存/队列/日志/指标” 模式。

| 接口                        | 描述                           | 关键流程                                                                                                                            |
| ------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **创建** `/task/create`     | 下发新任务                        | 1.接收参数（user\_id、device\_ids、cmd、priority、schedule）<br>2.权限校验<br>3.DB 插入 `tasks` 表<br>4.Kafka 推送 `task.new` 事件<br>5.返回 `task_id` |
| **更新** `/task/update/:id` | 修改任务配置                       | 1.预查询任务是否存在<br>2.状态检查（只能更新 `pending`）<br>3.DB 更新字段<br>4.事件 `task.updated`                                                       |
| **取消** `/task/cancel/:id` | 终止执行中或未执行任务                  | 1.预查询<br>2.更新 `status=canceled`<br>3.Kafka `task.canceled`<br>4.如果在队列中需从 Kafka Topic Dead-letter                                |
| **删除** `/task/delete/:id` | 删除历史任务                       | 同用户/设备删除逻辑                                                                                                                      |
| **查询** `/task/query`      | 任意字段单条查询                     | 同上                                                                                                                              |
| **列表** `/task/list`       | 条件分页查询                       | 支持按 `user_id`、`device_id`、`status`、`from/to` 过滤，Redis 缓存同 `/user/list`                                                          |
| **详情** `/task/detail/:id` | 获取任务所有元信息                    | 缓存 Key=`task:detail:{id}` → DB 查询 + Cache Fill                                                                                  |
| **结果** `/task/result/:id` | 查询任务执行结果（stdout/stderr、文件引用） | 1.从 ES 或对象存储（MinIO）拉取日志文件列表<br>2.按行读取或分页返回                                                                                      |
| **状态** `/task/status/:id` | 实时获取任务最新状态                   | 1.优先读 Redis（Worker 更新状态到 Redis Hash）<br>2.否则读 DB                                                                                |
| **分发** （内部 Job）           | 调度组件扫描 `pending` 任务并发到 Kafka | 1.定时 Job 扫描 DB<br>2.调用 `pkg/kafka/producer` 推送                                                                                  |
| **执行** （Client 端）         | Client 监听 Kafka，接收任务并执行      | 见 Client Executor 模块                                                                                                            |
| **日志** `/task/log/:id`    | 查看任务执行实时日志                   | 1.长轮询或 WebSocket，从 ES/Redis Stream 拉取                                                                                           |
| **统计** `/task/stats`      | 任务执行成功率、平均耗时等                | 聚合 Prometheus 指标，按用户/设备/时间窗口返回                                                                                                  |

---

以上即为三大模块下各接口的最细化流程拆解，明确了**表单/URI 参数**、**校验逻辑**、**数据库 & 缓存操作**、**消息队列通知**、**日志 & 指标打点** 等关键环节。如需对单接口做更深入的时序图或样例代码，再行补充。
