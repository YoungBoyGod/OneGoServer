## OneGo 分布式测试系统 详细开发顺序与任务分配

## 项目目录结构与文件说明

为支持后期扩展与模块独立管理，将代码分别放入两套仓库：

1. **onego-server** 仓库：负责中央控制服务器相关代码
2. **onego-client** 仓库：负责分布式客户端执行与上报逻辑

### onego-server 仓库结构

```
onego-server/
├── cmd/
│   └── server/
│       └── main.go                 # 启动应用
├── api/                             # 接口定义层
│   ├── v1/
│   │   ├── server.proto            # gRPC 与 OpenAPI 定义
│   │   └── server.pb.go            # 生成的代码
│   └── openapi.yaml                # RESTful API 描述
├── internal/
│   ├── biz/                         # 业务逻辑层（领域模型、用例）
│   │   ├── user.go
│   │   ├── device.go
│   │   └── task.go
│   ├── data/                        # 数据访问层（DB、Cache、MQ 封装）
│   │   ├── postgres/
│   │   │   └── postgres.go         # GORM 初始化与迁移
│   │   ├── redis/
│   │   │   └── redis.go            # 缓存与分布式锁
│   │   └── kafka/
│   │       ├── producer.go         # 消息生产者
│   │       └── consumer.go         # 消费者
│   ├── service/                     # 服务层（grpc/http 处理）
│   │   ├── handler.go              # 路由注册与中间件
│   │   └── service.go              # 将 biz 用例绑定到 transport
│   └── pkg/                         # 可复用包（工具、DTO、错误码）
│       ├── util/
│       └── api/
├── configs/                         # 配置模板
├── deployments/                     # k8s / docker-compose yamls
├── scripts/                         # 构建、迁移、部署脚本
├── Makefile
├── Dockerfile
├── README.md
└── go.mod/go.sum
```

### 分层式项目目录结构

参照 Kratos 分层规范，我们将两个仓库均采用以下分层目录：

```text
<module>-
├── api           # gRPC/protobuf 或 OpenAPI 接口定义
├── cmd           # 可执行程序入口
│   └── <app>/    # main.go
├── internal      # 私有应用代码
│   ├── service   # 业务逻辑（services）
│   ├── biz       # 领域模型与用例（domain）
│   ├── data      # 数据持久化与外部交互（repository）
│   └── server    # HTTP/gRPC transport 层
├── pkg           # 对外公用包（可复用）
└── configs       # 配置文件
```

以上结构沿用 Kratos 分层理念，层次清晰、职责分明，便于维护和扩展。

* **cmd/server/main.go**：启动流程，配置加载 → 日志/监控/DB/MQ 初始化 → 注册路由 → 启动 HTTP 服务
* **cmd/client/main.go**：加载客户端配置 → 连接 Server 注册 → 启动任务调度与执行循环
* **internal/config/config.go**：读取并解析多环境配置，支持热重载与敏感信息解密
* **internal/logger/logger.go**：全局 Logger 初始化，接入 Trace ID 与钩子
* **internal/db/postgres.go**：数据库连接管理、迁移执行、主从读写分离
* **internal/db/models/**：各业务实体模型和 CRUD 逻辑
* **internal/cache/redis.go**：Redis 客户端封装、Cache 一致性与分布式锁实现
* **internal/mq/producer.go**、**consumer.go**：Kafka 生产/消费封装、序列化与重试策略
* **internal/server/handler/**：HTTP 路由与请求解析，参数校验与响应封装
* **internal/server/service/**：核心业务逻辑实现，状态机、调度算法与生命周期管理
* **internal/server/middleware/**：鉴权、限流、CORS、安全头等中间件
* **internal/client/executor/executor.go**：本地并发执行器，日志与结果异步回传
* **internal/client/reporter/reporter.go**：上报模块，汇聚客户端执行状态与日志到 Server
* **pkg/util/crypto.go**：密码加盐、JWT 签名辅助、敏感字段加解密
* **pkg/util/validator.go**：统一输入校验，错误提示标准化
* **pkg/api/dto.go**：API 请求/响应结构体与错误码常量
* **scripts/**：本地构建、数据库迁移与 k8s 部署脚本，支持一键化操作
* **configs/**：各环境配置示例，方便快速切换与版本管理
* **charts/onego/**：Helm Chart 模板，定义部署资源与参数
* **Dockerfile**：生产镜像构建，多阶段优化体积与安全性
* **docker-compose.yaml**：本地联调与外部依赖模拟
* **Makefile**：常用命令封装（编译、测试、镜像、迁移）
* **README.md**：项目简介、架构说明、快速上手指南

此目录结构既遵循 Go 社区规范，又结合 OneGo 特有模块，便于团队开发、测试与运维协同。

本设计文档针对 OneGo 分布式测试系统的项目开发进行详细的任务拆分与注意事项说明，帮助团队在开发过程中明确职责、功能点与潜在风险，确保项目按期、高质量交付。

## 项目总览

### 系统架构

* **OneGoServer**: 中央控制服务器

  * 核心职责：任务调度、设备管理、权限控制、系统健康监控、日志聚合
  * 注意事项：高可用部署、水平扩展能力、API 并发性能
* **OneGoClient**: 分布式客户端

  * 核心职责：接收任务、执行测试用例、状态上报、日志与结果采集
  * 注意事项：断点续传、离线缓存、动态扩容、网络抖动容忍
* **支撑组件**: 数据库、缓存、消息队列、监控系统、日志系统

  * 注意事项：各组件高可用、灾备与容灾、组件版本兼容性、统一配置管理

### 技术栈

* **后端**: Go + Gin
* **数据库**: PostgreSQL (主库+热备) + Redis
* **消息队列**: Kafka
* **监控**: Prometheus + Grafana
* **日志**: Zap + ELK Stack
* **部署**: Docker + Kubernetes
* **安全**: TLS 证书管理、JWT、RBAC

## 阶段一：基础设施层 (第1-2周)

### 目标

* 搭建稳定、可扩展的技术框架
* 建立统一的工程规范、CI/CD、配置管理
* 完成数据存储与中间件集成

### 1.1 项目工程化 (第1周第1-3天)

**功能要求**：

* 规范化目录结构，支持微服务拆分
* 构建脚本支持一键构建、打包、镜像生成
* 开发/测试/生产多环境启动脚本

**注意事项**：

* Go 模块版本锁定，避免依赖冲突
* 在 Git hooks 中强制代码检查、格式化
* CI/CD 流水线需包含单元测试、Lint、构建、制品上传

### 1.2 配置管理 (第1周后2天)

**功能要求**：

* 支持 YAML/JSON/Env 多种配置格式
* 配置热加载，避免重启服务
* 环境隔离，配合 Kubernetes ConfigMap/Secret

**注意事项**：

* 敏感信息加密存储，且不落入日志
* 配置校验失败要明确报错，并阻止服务启动
* 配置变更需兼容历史版本

### 1.3 数据存储与中间件 (第2周)

**PostgreSQL 集成** (2天)

* GORM 或 SQLBuilder 集成及统一封装
* 主从/读写分离策略，连接池配置
* DB schema 迁移工具（如 Flyway）

**Redis 缓存** (1天)

* 缓存分层设计：本地 + 集群
* 缓存穿透、雪崩、击穿防护策略
* 分布式锁实现（基于 RedLock）

**Kafka 消息队列** (1天)

* 主题规划：任务调度、日志上报、状态通知
* 消息序列化：Protobuf 或 JSON，兼顾可演进
* 消费者幂等/重复消费处理、重试机制

## 阶段二：核心业务层 (第3-6周)

### 目标

* 实现用户、设备、任务三大核心功能
* 完善安全策略，确保系统访问可控
* 提供健全的 API 文档与错误管理

### 2.1 用户认证与授权 (第3周)

**用户管理** (2天)

* 注册、登录、找回密码、绑定多因素认证
* 用户资料修改、头像上传、历史登录记录

**JWT 与 Token 管理** (1天)

* Token TTL、刷新策略、黑名单
* 多设备登录管理、强制下线

**权限控制** (1.5天)

* RBAC 角色与资源映射
* API 层中间件统一拦截
* 动态权限：管理员可在线配置、下发

**安全加固** (0.5天)

* 请求限流（IP 与用户级别）
* CORS、CSRF 防护、HTTP 安全头

**注意事项**：

* 密码强度校验、加密算法更新（bcrypt/argon2）
* Token 泄露风险评估与审计日志

### 2.2 设备管理核心 (第4周)

**设备注册** (2天)

* 收集设备字段：IP、硬件指纹、OS、客户版本
* 去重策略、防止同一台设备多次注册

**心跳 & 在线状态** (1天)

* 设计心跳协议：周期、超时判定、重连策略
* 异常上报：网络断连、版本不匹配

**设备状态机** (1.5天)

* 状态定义：离线/空闲/运行/维护/故障
* 事件驱动的状态变更处理

**设备 API & 批量操作** (0.5天)

* 前端分页、筛选、多字段查询支持
* 批量标签、批量上下线、批量重启

**注意事项**：

* 设备数据表设计要支持弹性扩展字段
* 心跳改版需兼容老版本客户端

### 2.3 任务调度引擎 (第5-6周)

**任务模型设计** (1天)

* 参数化：并行度、资源需求、超时时间
* 优先级：实时/延后/定时任务

**调度算法** (2天)

* 资源匹配：CPU/GPU/内存/带宽
* 负载均衡：轮询、权重、最空闲优先
* 失败重试：重试次数、回退时间、告警

**执行管理** (2天)

* 执行上下文隔离（工作目录、环境变量）
* 日志实时采集、归档到 ELK
* 断点续跑与二次调度

**队列管理** (1.5天)

* 多优先级队列架构
* 持久化存储、断点恢复
* 队列监控、滞后告警

**任务 API** (1.5天)

* 创建、查询、取消、重跑接口
* 批量操作与批量回调
* 历史记录与统计分析

**注意事项**：

* 参数校验需全面，避免恶意注入
* 调度引擎需有自我保护，防止雪崩

## 阶段三：高级功能层 (第7-9周)

### 目标

* 提升系统可观测性、可维护性与性能

### 3.1 监控系统 (第7周)

**指标采集** (2天)

* 业务维度指标：任务成功率、平均耗时
* 系统维度指标：CPU、内存、GC、连接数

**Prometheus 集成** (1天)

* 指标暴露标准：/metrics 接口
* 标签规划：服务名、节点、环境

**Grafana 大屏** (1.5天)

* 实时看板：整体健康、关键任务统计
* 告警策略：阈值告警、SLA 监控

**健康检查** (0.5天)

* Liveness、Readiness Endpoint
* 依赖下游服务健康聚合

### 3.2 日志管理 (第8周)

**结构化日志** (1天)

* Zap 日志标准化：timestamp、level、traceId
* Trace 链路上下文传递

**日志收集与传输** (1.5天)

* Filebeat + Logstash + Elasticsearch
* 日志分级：INFO/ERROR/DEBUG 清晰区分

**日志分析** (1天)

* Kibana 搜索模板与常用 Dashboard
* 异常日志统计、错误聚合报告

**审计日志** (0.5天)

* 关键操作记录：用户管理、权限变更
* 审计合规报告导出

### 3.3 性能优化 (第9周)

**数据库调优** (1.5天)

* 慢查询日志定位、优化 SQL 与索引
* 分库分表方案评估

**缓存与并发** (1天)

* 多级缓存设计、热点数据预热
* 并发限流、队列削峰

**API 性能** (1天)

* 接口压测（JMeter/Locust）、P95/P99 报告

**负载均衡** (0.5天)

* 多地域部署、DNS+LB 方案
* 健康检查与流量切换策略

## 风险与应对

| 风险类型   | 风险明细                   | 应对策略             |
| ------ | ---------------------- | ---------------- |
| 分布式一致性 | 任务状态同步、分库分表一致性         | 强制幂等、最终一致性、事务补偿  |
| 性能瓶颈   | 高并发下系统响应下降             | 预留扩容、压测调优、缓存优化   |
| 依赖集成复杂 | 中间件版本冲突、配置不一致          | 分阶段集成、版本锁定、端到端测试 |
| 安全漏洞   | 配置泄露、XSS/CSRF、Token 漏洞 | 定期安全扫描、漏洞紧急修复流程  |
| 进度延误   | 关键任务阻塞、人员流失            | 并行备选、技术预研、外部支持   |
| 需求变更   | 中途需求波动                 | 敏捷迭代、变更评审委员会     |
