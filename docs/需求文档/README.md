## 📖 文档编写规范

### 📌 基本要求

1. **语言要求**：所有文档必须使用中文编写
2. **格式要求**：使用Markdown格式，统一文档结构
3. **内容要求**：重点描述业务逻辑和技术架构，避免过多具体代码实现
4. **流程图要求**：每次重要修改都需要生成对应的Mermaid流程图

### 📋 文档结构模板

每个需求文档必须包含以下10个标准章节：

```markdown
# 模块名称需求文档

## 1. 功能描述
- 模块主要功能
- 业务场景说明
- 功能边界定义

## 2. 功能目标
- 业务目标
- 技术目标
- 性能目标

## 3. 输入输出
- 输入参数定义
- 输出结果规范
- 数据格式说明

## 4. 接口设计
- API接口规范
- 请求/响应格式
- 状态码定义

## 5. 数据结构
- 数据库表结构
- 实体类定义
- 数据关系说明

## 6. 异常处理
- 异常类型定义
- 错误处理机制
- 容错策略

## 7. 流程图
- 业务流程图（Mermaid）
- 时序图
- 数据流图

## 8. 安全性考虑
- 权限控制
- 数据安全
- 安全防护措施

## 9. 日志与监控
- 日志记录规范
- 监控指标定义
- 告警机制

## 10. 测试用例
- 功能测试用例
- 性能测试用例
- 安全测试用例
- 异常测试用例
```

### 🎯 文档编写要求

#### 内容描述方式
- ✅ **推荐**：使用文字描述 + 伪代码
- ✅ **推荐**：业务逻辑流程说明
- ✅ **推荐**：技术架构设计思路
- ❌ **避免**：具体的Go代码实现
- ❌ **避免**：过于详细的代码片段

#### 技术实现描述
- **Controller层**：重点描述参数验证、权限控制、错误处理策略
- **Logic层**：详细描述业务处理步骤，包含数据库/缓存/队列操作
- **DAO层**：描述数据访问策略、读写分离、事务处理
- **缓存策略**：说明缓存Key设计、TTL策略、失效机制
- **消息队列**：描述队列设计、事件类型、消费者处理

#### 流程图规范
- 使用Mermaid语法编写
- 包含完整的数据流向
- 体现系统各组件交互
- 突出关键业务节点

### 📝 文档生成要求

每次完成需求文档编写或重大修改后，必须生成以下文档：

1. **修改清单**：列出当前修改的要点和优点
2. **流程图**：展示修改内容的可视化说明
3. **总结文档**：包含修改内容、技术亮点、后续建议的md文件

### 🔄 文档维护原则

1. **单一职责**：保持API层和内部模型分离，不合并
2. **版本控制**：重要修改需要记录版本变更
3. **一致性**：所有模块文档遵循统一格式
4. **可读性**：重点突出，层次清晰，便于理解
5. **完整性**：保留完整技术架构，避免遗漏关键信息

### 🎯 质量标准

- **完整性**：包含所有必需的10个章节
- **准确性**：技术描述准确，业务逻辑清晰
- **一致性**：格式统一，术语一致
- **可读性**：结构清晰，易于理解
- **维护性**：便于后续更新和维护
